## 1. META002/005/006/007 don't understand modern `charmcraft.yaml` (`title`, `links`)

**Severity:** false positives on every compliant modern charm.

`src/charmlint/rules/metadata.py` checks for **top-level** keys from the legacy
`metadata.yaml`, but in a unified `charmcraft.yaml` those moved:

| Rule | Looks for top-level | Modern location |
|------|---------------------|-----------------|
| META002 | `display-name` | `title` |
| META005 | `docs` | `links.documentation` |
| META006 | `issues` | `links.issues` |
| META007 | `source` | `links.source` |

The check is just `if not context.metadata.get(fld)`, so a charm that correctly
sets `title:` and a `links:` block (documentation/issues/source/website/contact)
gets four false positives. Reproduced on all four charms.

**Fix:** META002 accept `title` (or `display-name`); META005/006/007 read
`links.documentation` / `links.issues` / `links.source`, falling back to the
legacy top-level keys for old `metadata.yaml` charms. Compare with
`canonical/charmhub-listing-review`'s `metadata_links` check, which reads
`links.<field>`.

## 2. SEC001 doesn't recognize the ops secrets API

**Severity:** false positive even when the charm uses Juju secrets correctly.

`src/charmlint/rules/security.py` decides whether the charm uses Juju secrets
with:

```python
has_juju_secrets = bool(re.search(r"juju.*secret|Secret(?:Changed|Rotate)", all_source))
```

The ops framework's secrets API is `self.app.add_secret(...)`,
`self.model.get_secret(...)`, `Secret.get_content()`, `event.secret`, the
`SecretChanged`/`SecretRotate` events, etc. — none of which contain the literal
substring `juju...secret`. So a charm that uses ops secrets extensively still
reports `has_juju_secrets = False`, and any config option whose name contains a
secret keyword (e.g. `smtp-password`) is flagged.

Reproduced: `sentry-k8s` uses `add_secret`/`get_secret` throughout and even makes
`smtp-password` a `type: secret` config option, yet SEC001 still fires.

**Fix:** detect the ops secrets API — e.g. `\b(add_secret|get_secret|grant|
SecretChanged|SecretRotate)\b`, a config option of `type: secret`, or
`ops.Secret`. Also consider: a config option declared with `type: secret` should
not be flagged at all (its value is a secret URI, not plain text).

---

## 3. DOC002/DOC005 (and likely others) are not monorepo-aware

**Severity:** false positives for charms in a monorepo.

`src/charmlint/rules/documentation.py` looks only in `context.charm_dir / "docs"`.
In a monorepo where charms live under `charms/<name>/` and share a single
top-level `docs/` tree (tutorial/how-to/reference), every charm is flagged as
missing installation and troubleshooting docs.

**Fix:** when no `docs/` is found in the charm dir, walk up to the repository
root (e.g. nearest `.git`) and check there; or add a config/flag for the docs
location. (META links already point at the shared docs, so the information is
discoverable.)

---

## 4. PEB002 doesn't recognize a `can_connect()` guard in a calling function

**Severity:** false positive for correctly-guarded code.

`src/charmlint/rules/pebble.py` (PEB002) flags a function that calls a Pebble
method (e.g. `.exec()`) without a `can_connect()` guard *in that same function*.
Charms commonly guard once in `_reconcile` and call helpers:

```python
def _reconcile(self, _):
    if not self.container.can_connect():
        return
    ...
    self._migrate(...)        # guarded by the caller

def _migrate(self, ...):
    self.container.exec(...)  # flagged by PEB002, but the caller guarded it
```

Reproduced on `sentry-k8s._migrate`, `sentry-snuba-k8s`, `sentry-relay-k8s`.

**Fix:** this is inherent to per-function analysis. Options: follow call edges
to see whether all callers guard before calling; or treat a method that only
runs after a guarded entry point as guarded; or downgrade to info and document
the limitation. At minimum, recognising a guard on the same container object
anywhere on the path would remove the common false positive.
