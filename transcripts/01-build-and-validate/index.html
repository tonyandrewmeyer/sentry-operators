F. Gotchas for running these images in Kubernetes (outside compose)

  1. Shared sentry-data volume (RWX). All Sentry-app pods (web, taskworker, taskscheduler, every consumer, sentry-cleanup) mount sentry-data:/data. With stock filestore.backend: filesystem (location /data/files) and the dsym/releasefile caches under /data, this must be ReadWriteMany across web+workers, or you must switch filestore.backend to s3 (seaweedfs/your own) so each pod is stateless. Strongly recommend the S3 filestore route for K8s. (Nodestore and profiles are already S3.)
  2. Config dir /etc/sentry is bind-mounted in compose (entrypoint, config.yml, sentry.conf.py). In rocks, bake these in or mount via ConfigMap/Secret. system.secret-key, relay credentials.json, and relay/config.yml are secrets.
  3. Migration ordering is hard ordering, not soft. snuba bootstrap (topics + ClickHouse schema) and sentry upgrade (Postgres + Sentry topics) must complete before any consumer or web starts serving. Implement as a Juju action / init-job with leader-election so it runs once. The compose healthchecks (depends_on: service_healthy) only gate startup connectivity, not migration completion.
  4. Kafka topic auto-creation. Topics are explicitly created by snuba bootstrap and sentry upgrade --create-kafka-topics. The single-node Kafka uses replication factor 1, 1 partition for __consumer_offsets. Don't rely on broker auto-create. If you externalize Kafka, pre-create topics or run the bootstrap commands.
  5. Kafka is KRaft single-node (CLUSTER_ID=MkU3OEVBNTcwNTJENDM2Qk, node 1001). For a charm you'll likely relate to a real Kafka cluster — then partitions/replication and consumer-group offsets behave differently; the --no-strict-offset-reset flags matter for resilience.
  6. ClickHouse single-node settings. Mounts config.xml (single-shard/replica, MAX_MEMORY_USAGE_RATIO=0.3) and default-password.xml. SSE 4.2 required. ulimits nofile 262144. The Altinity build is used, not vanilla ClickHouse.
  7. Healthchecks differ by service type. HTTP services use TCP/HTTP probes (web: /_health/ on 9000; snuba-api: api_healthcheck.py; relay/vroom: /health). Consumers/taskworkers use a file-based liveness probe: they touch /tmp/health.txt, and the probe deletes it and fails if it's missing (HEALTHCHECK_FILE_START_PERIOD=600s, i.e. 10 min grace). Replicate this as a K8s liveness exec probe, or pass the --healthcheck-file-path/--health-check-file flag (already in commands) and probe accordingly.
  8. Relay healthcheck/memory bug. Relay may misdetect container memory and fail its healthcheck, blocking ingest. Workaround in relay/config.yml: set health.max_memory_percent: 1.0 and a spool path. Bake this into your relay config for K8s.
  9. sentry-cleanup cron. It's a long-running cron container (0 0 * * *). In K8s replace with a CronJob running sentry cleanup --days $SENTRY_EVENT_RETENTION_DAYS. Likewise symbolicator-cleanup (--repeat 1h) and ClickHouse cleanup.
  10. pgbouncer in the path. Sentry connects to pgbouncer:5432 (transaction pooling, AUTH_TYPE=trust). Migrations (sentry upgrade) historically need a direct Postgres connection for some advisory-lock/index operations — the install script starts both and the migration step has special handling (issue #2758). Be careful running Django migrations through a transaction-pooling pgbouncer; point migration jobs at Postgres directly.
  11. Internal vs external URL. system.internal-url-prefix: http://web:9000 is for service-to-service; system.url-prefix is the public URL. Relay's relay.upstream also points at http://web:9000/. Map these to K8s Service DNS names.
  12. GeoIP file must exist. An empty geoip/GeoLite2-City.mmdb is required or relay's geoip_path load fails; ship the empty mmdb in the rock and optionally wire geoipupdate with a MaxMind license.
  13. Taskbroker SQLite is stateful. sentry-taskbroker volume holds up to ~2048 inflight tasks; losing it loses those tasks. Give taskbroker a small persistent volume (it's effectively a single-writer; don't scale it horizontally without care).
  14. Two consumer "tiers" share consumer-group names deliberately (e.g. post-process-forwarder group across the three PPF variants; snuba-consumers across several snuba consumers). Preserve the exact --consumer-group and --synchronize-commit-* flags — the post-process forwarders synchronize against Snuba's commit-log topics (snuba-commit-log, snuba-transactions-commit-log, snuba-generic-events-commit-log) to avoid post-processing events Snuba hasn't durably written yet. Getting these wrong causes lost or duplicated post-processing.
